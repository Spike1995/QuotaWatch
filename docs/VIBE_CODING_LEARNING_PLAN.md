# Quota Watch：Vibe Coding 学习与工程一体化计划

> 目标：以 Quota Watch 为唯一主线，从“能让 AI 生成代码”逐步成长为“能定义任务、审查代码、验证结果、定位故障并独立交付产品”的开发者。
>
> 适用起点：零基础或基础较弱；当前仓库已有 Flutter 静态 UI 草案，但尚未完成 Flutter 工具链安装与运行验证。

### 当前学习者画像（2026-07-22 访谈基线）

- 目标不是脱离 AI 手写全部代码，而是持续使用 AI 时仍能定义任务、判断方案、验证结果和交付开源软件。
- 有 C 语言学习经历但知识已较模糊；用过终端与 Git，也借助 AI 完成过博士论文 TeX 工作流。
- 当前尚不能解释源代码如何运行、测试为什么必要；对 HTTP/API 有初步印象，需纠正“JSON 是脚本”的误解。
- 可稳定投入每周 6 天、每天约 2 小时；英文技术文档阅读无明显障碍。
- 三家 Coding Plan 均已订阅，Codex 最重要；首版开发在 Windows 上进行，最终希望他人能够安装、使用和贡献。
- 学习方式采用边做边学，重点熟悉需求到发布的全栈开发流程，而不是专攻某一种语言或框架。每次只要求当前交付切片所需的简短反向讲解，不用先背完整理论。

## 1. 如何使用这份计划

这不是按日期打卡的课程表，而是一组按依赖关系排列的能力关卡。按当前每周约 12 小时投入估算：

- 阶段 0～5 的“假数据完整开发闭环”约 8～12 周；
- 阶段 6～9 的“真实数据与开源 Beta”再约 8～12 周；
- 阶段 10 的产品 MCP 是可选扩展，约 2～4 周。

这些数字不是截止日期。实际速度取决于环境问题、理解验证和第三方接口变化，只有满足阶段验收条件才进入下一阶段。

本仓库当前运行在 Windows + PowerShell 环境，因此阶段 0～8 只把 Windows 作为必验平台。Web、Android 在开源发布阶段逐个增加；iOS 最后选做。拥有设备不等于必须同时支持，平台扩展不能阻塞基础学习。

每个阶段同时回答五个问题：

1. **我要理解什么？**——必须由你本人掌握的知识。
2. **工程要增加什么？**——最终产品真正需要的代码或文档。
3. **AI 应该怎样参与？**——把 AI 当教师、结对程序员、审查者和调试助手。
4. **我必须亲手做什么？**——防止只会复制代码。
5. **怎样证明完成？**——用命令、测试、截图或解释记录提供证据。

时间只是参考，验收证据才是进度。配套记录文件见 [LEARNING_LOG.md](LEARNING_LOG.md)。API 细节以 [API_RESEARCH.md](API_RESEARCH.md) 为准。

### 1.1 全栈流程优先的学习取向

- 学习骨架是：需求与验收 → 前端界面与状态 → 数据契约 → 后端/API → 联调 → 自动化测试与故障定位 → Git/diff → 构建、文档与发布。
- Dart、Flutter、Python、FastAPI、HTTP 等都是完成这条链路的工具，不单独安排脱离项目的系统语法课。
- 每张任务卡必须标明它位于上述哪一环、输入和输出是什么、为下一层准备什么，并至少验证一个失败或边界路径。
- 语法在真实代码第一次出现时解释到能读懂和验收即可；详细中文注释作为随查资料，不要求集中记忆。
- 在前置条件满足后优先做可运行的纵向小切片，避免长期只在某一层打磨而看不到端到端结果。
- 当前采用“实现优先”：Codex 先完成一个小而可验证的功能；遇到错误、风险、产品选择或用户主动提问时，再结合当前代码解释。
- 交付说明保持简短，不用突然提问代替教学；需要复盘时再共同整理“改了什么、为什么、怎样证明”。

## 2. 最终产品与毕业标准

### 2.1 最终工程形态

```text
阶段 0～3：Flutter App ──> Mock / Fixture Repository

阶段 4～5：Flutter App ──HTTP/JSON──> 本地 FastAPI 假接口

阶段 6～9：Flutter App ──HTTPS/JSON──> FastAPI 聚合服务
                                      ├── Codex 适配器（优先）
                                      ├── Kimi 适配器
                                      └── GLM 适配器
                                      ├── 凭据、缓存、超时、降级、日志
                                      └── 统一 ProviderQuota 契约

阶段 10（可选）：产品 MCP Server ──> 复用聚合服务的只读额度能力
```

这里的“产品 MCP Server”与开发时使用的 `kimi_worker`、`glm_worker` 不同：前者是未来产品功能，
后两者是 Codex 可调用的辅助开发模型。

公开 Web/移动端不得内置 Kimi、GLM 或 Codex 凭据。产品路径统一通过后端；仅允许在本地、短期、不会提交或部署的实验中直接请求第三方 API。

### 2.2 产品完成标准

先验收“学习版”，再验收“开源版”。

**阶段 5 学习版：**

- Windows 上可以运行 Flutter App，并通过本地 FastAPI 假接口展示三家模拟额度。
- 页面包含正常、加载、空、未配置和失败状态；不使用真实 Key。
- Flutter 与 FastAPI 都有基础自动化测试，README 能让自己从零重新运行。
- 至少一次功能完成了任务卡、实现、diff、测试、三句话讲解和复盘。

**阶段 9 开源 Beta：**

- 首页和详情页能展示三家额度、剩余量、重置时间及查询状态。
- 单家接口失败不会拖垮其他服务；页面能区分加载、未配置、降级和失败状态。
- 凭据不进入 Git、前端构建产物、日志、截图或测试夹具。
- Flutter 与 FastAPI 都有自动化测试；关键解析器包含正常、字段变体、缺字段、401、429、超时测试。
- Windows 程序优先可构建和安装；Web、Android 随后逐个验证，iOS 作为可选扩展。
- MCP Server 能以只读工具查询同一份额度数据。
- README 能让一台干净机器上的读者完成安装、配置、运行和测试。

### 2.3 Vibe Coding 毕业标准

你能够在没有现成答案的情况下：

- 把模糊想法写成包含范围、约束和验收标准的任务卡。
- 要求 AI 先调查和计划，再做小批量修改。
- 阅读 `git diff`，指出关键修改、风险和不理解之处。
- 即使命令由 AI 提议，也能亲自运行关键验证，并判断失败更像环境、语法、逻辑、接口还是配置问题。
- 对关键代码进行简短“反向讲解”：改了什么、为什么、怎样证明；随能力增长再补充输入、输出和失败路径。
- 发现 AI 幻觉、过度设计、未验证结论和凭据泄漏风险。
- 在一次独立功能挑战中完成“需求 → 实现 → 测试 → 文档 → 复盘”闭环。

## 3. Vibe Coding 的固定工作循环

每一个工程任务都执行同一个循环：

```text
观察现状 → 明确需求、输入/输出和验收 → 选择最小全栈切片
    → 按需让 GLM 或 Kimi 只读提建议 → Codex 筛选并修改
    → 连接当前所需的 UI/契约/API 层 → Codex 运行完整验证
    → 你亲自运行一个关键验收 → 审查 diff/Git → 三句话讲解
    → 记录交付证据和下一层依赖
```

### 3.1 开工前：任务卡

每次只做一个可在 30～120 分钟内验证的切片：

```markdown
目标：这次结束时用户能看到或系统能做到什么？
现状证据：相关文件、当前行为、错误原文是什么？
范围：允许修改哪些模块？明确不做什么？
约束：安全、兼容性、依赖、界面或时间要求是什么？
验收：运行哪些命令、观察哪些行为才算完成？
学习点：结束后我必须能解释哪三个概念？
```

### 3.2 人与模型的固定职责

| 参与者 | 固定职责 | 不允许代替的证据 |
|---|---|---|
| 你 | 产品取舍、亲自运行关键验收、三句话反向讲解、最终接受或拒绝 | “我看起来觉得可以”不能代替命令、测试或操作结果 |
| Codex | 主控与教师；调查、拆任务、编辑工作区、运行测试、整合 worker 建议、最终审查 | worker 的结论不能代替 Codex 对代码与测试的核验 |
| GLM worker | 后端、通用编程、异常路径和测试设计的只读顾问 | 不直接写文件、执行 Shell 或提交；建议必须经 Codex 落地验证 |
| Kimi worker | Flutter UI、交互、响应式、可访问性和视觉一致性的只读顾问 | UI 描述不能代替可运行界面与 Widget 测试 |

委托规则：任务必须边界清楚；默认只找一个最相关 worker；探索和审查可以并行，多个模型不得同时修改同一代码。worker 超时或失败时，Codex 继续主流程，不把辅助模型变成阻塞依赖。

### 3.3 七条硬规则

1. 不把 API Key、Token、Cookie、`auth.json` 内容发送给模型或写入仓库。
2. 不接受“应该可以”；必须运行与改动范围匹配的验证。
3. 一次修改尽量只解决一个任务卡，避免无法审查的大改。
4. 看不懂的关键代码不合并：先让 AI 解释，再用小实验验证。
5. AI 给出的第三方接口、版本和部署结论必须用官方资料或真实响应复核。
6. 阶段 0～5 不接真实额度 API；先用 Mock、Fixture 和本地假接口证明完整开发闭环。
7. 每张任务卡结束时必须完成三句话：改了什么、为什么这样改、什么证据证明它有效。

## 5. 详细学习与实施路线

## 阶段 0：让当前工程真正运行

**参考投入：** 2～4 次学习会话
**当前事实：** Flutter Web 脚手架、测试目录和分析配置已经补齐；Flutter 3.44.2 可用，Web/Edge 已完成运行验收；Windows、Android、iOS 平台暂按后续任务卡处理。

### 学习清单

- 路径、当前目录、命令、退出码、环境变量分别是什么。
- 源代码、SDK/编译器、依赖、构建产物和正在运行的程序分别是什么。
- Flutter SDK、Dart SDK、`pubspec.yaml`、包依赖和平台目录的关系。
- `flutter pub get`、`flutter analyze`、`flutter test`、`flutter run` 各自验证什么。
- “程序能启动”只证明启动路径，不证明所有输入、状态和失败场景都正确。
- Git 的工作区、暂存区、提交和 `.gitignore` 基本概念。
- 如何保存完整报错，而不是只描述“运行不了”。

### 工程步骤

1. 安装 Flutter，并用 `flutter doctor -v` 记录缺失项。
2. 先在仓库根目录初始化 Git 并提交现有草案；若 Git 身份尚未配置，至少制作一份只读备份。
3. 在 `quota_watch/` 中先运行 `flutter create --help` 核对本机版本参数，再只补当前学习所需的平台脚手架；
   优先在 Windows 主机上用 Chrome 快速验证，Windows 桌面构建最迟在阶段 5 完成，Android/iOS 暂不处理。
4. 立即查看 `git diff`；保留新增平台文件，逐项审查 `pubspec.yaml`、`lib/` 等已有文件是否被意外改写。
5. 拉取依赖并运行静态分析。
6. 修复阻止编译的代码，优先检查当前手写 `RouterDelegate`。
7. 在 Chrome 启动首页，点击三张卡片进入详情页，测试下拉刷新和深色模式。
8. 建立第一个可运行基线提交。

### AI 协作练习

- 先让 AI 根据 `flutter doctor -v` 分类环境问题，不允许它立即改项目代码。
- 遇到编译错误时，要求 AI 给出“错误含义、三个可能原因、最小验证命令”。
- 修复后要求 AI 只审查本次 diff，说明为什么不会破坏其他页面。

### 必须亲手完成

- 自己输入所有运行命令并记录退出结果。
- 画出 `main()` → `MaterialApp` → `HomePage` 的启动路径。
- 用三句话解释“代码文件存在、程序能启动、功能经过验证”为什么是三件不同的事。

### Definition of Done

- `flutter doctor -v` 对目标平台没有阻断项。
- `flutter pub get` 成功。
- `flutter analyze` 无 error。
- `flutter test` 能执行；即使暂时没有测试，也要建立 `test/` 基线。
- `flutter run -d chrome` 能打开页面，首页与详情导航可操作。
- 能指出源代码经过哪些工具和步骤后成为屏幕上正在运行的界面。
- 学习日志保存命令、问题、修复和一张运行截图路径。

## 阶段 1：读懂并控制现有 Flutter UI

### Definition of Done

- 能用自己的话讲清数据从模拟仓库到进度条的完整路径。
- 模型和核心导航测试通过。

- `flutter analyze` 与 `flutter test` 通过。

## 阶段 2：建立可审查、可测试、可回退的 Vibe Coding 基线

**参考投入：** 2～4 次学习会话

### 学习清单

- 好任务的粒度、验收标准与非目标。
- `git status`、`git diff`、分支、提交信息和安全回退。
- 单元测试、Widget 测试、集成测试分别保护什么。
- 依赖倒置与 Repository 接口为何能隔离 UI 和数据源。
- AI 常见失败：扩大范围、虚构 API、吞掉错误、只测快乐路径。

### 工程步骤

1. 定义抽象 `QuotaRepository`，让 Mock 实现它。
2. 把页面的数据获取与展示解耦，为后续真实数据源留接口。

- 让 AI 扮演“容易误用工具的模型”，检查描述是否含糊。
- 对比过大工具和两个最小工具的调用可靠性。
- 让另一个模型只根据工具 Schema 预测调用方式，作为读者测试。

### 必须亲手完成

- 自己写出工具参数、返回值和错误语义。
- 解释为什么 MCP 不应直接读取或回显所有秘密。
- 检查至少三段工具调用轨迹，判断模型选择是否合理。

### Definition of Done

- Agent 能回答“三家目前剩余多少、何时重置”。
- 单家失败时工具返回部分结果与明确状态。
- MCP 测试不访问真实第三方服务。
- README 包含注册、启动、调用示例和安全说明。

## 7. 每周节奏与复盘方法

固定节奏为每周 6 天、每天约 2 小时，至少保留 1 天休息。建议每周完成 2～4 张任务卡，而不是追求“学完一章”。其中 4 天推进功能，1 天集中测试/修复，1 天做 20 分钟无 AI 小练习并完成周复盘；实际卡住时可以调整，不为打卡牺牲理解。

### 一次学习会话（60～120 分钟）

1. **10 分钟：观察**——运行当前版本，选一个真实问题。
2. **10 分钟：任务卡**——由 Codex 帮你写目标、范围、验收和学习点，你确认取舍。
3. **15 分钟：教学与方案**——Codex只解释本卡会用到的概念；必要时委托一个相关 worker 只读复核。
4. **50 分钟：实现**——Codex 一次只做最小切片，你随时追问不理解的 diff。
5. **20 分钟：验证**——Codex 跑完整检查；你亲自运行一个关键命令或操作路径。
6. **10 分钟：审查与讲解**——看 diff，用三句话说明改了什么、为什么、怎样证明。
7. **5 分钟：记录**——填写日志与下一步。

### 每周复盘四问

- 这周哪些结果有命令或测试证明，哪些只是“看起来完成”？
- AI 哪次建议是错的、过度的或没有证据的？我是怎样发现的？
- 哪段关键代码我仍无法独立解释？
- 下周最小、最有价值的工程切片是什么？

### 每阶段毕业口试

让 AI 连续追问：

1. 这个阶段最关键的数据流是什么？
2. 最容易失败的三个位置在哪里？
3. 哪些测试证明了成功？还有什么没被证明？
4. 如果删掉某个组件，会发生什么？
5. 当前阶段最可能变化的外部条件是什么？进入真实 API 阶段后，再专门追问第三方响应变化。

答不清的内容回到小实验，而不是背答案。

## 8. 可复用 Prompt 模板

### 学习解释

```text
结合 Quota Watch 的 <文件/功能> 解释 <概念>。
先说明它解决的问题，再沿本项目数据流举例，最后给我 3 个检查理解的问题。
不要直接改代码。
```

### 实现任务

```text
目标：...
现状证据：...
允许修改：...
不做：...
验收：...
学习点：...

先检查相关文件并给出最小方案、风险和计划修改的文件；等范围明确后再实现。
修改后运行与范围匹配的测试，并总结 diff。
```

### 调试

```text
这是完整错误和复现步骤：...
请区分事实与假设，按可能性列 3 个原因。
每个原因只给一个最小验证步骤；先不要大改代码。
不要索要或输出任何凭据。
```

### 代码审查

```text
只审查这份 diff，不修改文件。
寻找：逻辑错误、未覆盖边界、秘密泄漏、竞态、兼容性和无效测试。
按严重度排序；每条必须说明触发条件和证据。没有问题就明确说没有。
```

### 委托 GLM 后端审查

```text
只读审查这张已明确范围的后端任务卡与相关文件，不修改工作区。
重点检查：数据契约、错误传播、边界情况、测试遗漏和过度设计。
返回按严重度排序的建议，并说明证据；不要索取或输出凭据。
```

### 委托 Kimi UI 审查

```text
只读审查这张已明确范围的 Flutter UI 任务卡与相关 Widget，不修改工作区。
重点检查：信息层级、状态表达、响应式、可访问性和交互反馈。
每条建议必须可通过运行、截图对比或 Widget 测试验收。
```

### 复盘

```text
根据任务卡、diff 和测试结果，帮我复盘：
1. 哪些目标被证据证明；
2. 哪些仍未证明；
3. 我依赖 AI 但尚未理解的部分；
4. 下一张最小任务卡。
```
